# 분산 키-값 저장소
분산 시스템을 설계할 때에는 CAP 정리에 대해서 이해하고 있어야 한다.

# CAP 정리
**Consistency** 일관성
접속하는 모든 클라이언트는 언제나 같은 데이터를 볼 수 있어야 한다.

**Availability** 가용성
분산 시스템에 접속하는 클라이언트는 일부 장애가 발생하더라도, 항상 응답받을 수 있어야 한다.

**Partition tolerance**
네트워크에 파티션이 생기더라도, 시스템은 계속 동작해야 한다.
(네트워크에 통신 장애가 생겨서 단일 그룹 ->그룹A, 그룹 B 로 나뉘는 것)

### CP, AP, CA
CP : 가용성 희생
AP : 데이터 일관성 희생
CA : 실세계에 이런 시스템은 없다.

![[Pasted image 20250831110618.png]]
 n3 에 장애가 발생한 것을 예시로 들어 보자.
 n3에 있고, n1, n2에 전달되지 않은 데이터가 있을 것이다.
 
 CP
 - 데이터 불일치를 피하기 위해 n1과, n2에 대해 쓰기 연산을 중단시켜야 한다.
 - 그래서 일관성이 깨질 상황에서는 오류를 반환해야 한다.

AP
- 이상한(낡은) 데이터를 반환하더라도, 계속 읽기를 허용한다.
- 물론, 쓰기도 허용한다.
- 파티션 문제가 해결된 후에 불일치 문제를 해결할 것

## 데이터 일관성
### 정족수 합의 프로토콜 (Quorum Consensus)
![[Pasted image 20250831111700.png]]
![[Pasted image 20250831111721.png]]
 **W = 1, R = 1**
- 한 대 서버에만 쓰기/읽기 된다는 것이 아니다.
- Coordinator가 s0, s1, s2에 보냈는데, W = 1 일 때, 1개의 서버에 성공 ACK를 받았다면 그 즉시 종료.

### R = 1 W = N
빠른 읽기 연산

### W = 1, R = N
빠른 쓰기 연산

### W + R > N 
강한 일관성

### W + R <= N
강한 일관성이 보장되지는 않음

## 일관성 모델
### 강한 일관성
클라이언트는 절대로 낡은 데이터를 볼 수 없음
### 약한 일관성
가장 최근에 갱신된 결과를 읽을 것이라고 보장 못함
### 최종 일관성
갱신 결과가, 결국에는 모든 사본에 반영되는 모델

다이나모, 카산드라 => 최종 일관성 모델

### 벡터 시계
> **[ 서버, 버전 ]** 

순서쌍을 데이터에 매단 것이다.

D([S1,v1], [S2, v2], ... , [Sn, Vn]) 으로 표현

D를 서버 Si에 기록하면,
- [Si, vi] 가 있으면 vi 증가.
- 그렇지 않으면 [Si, 1] 만든다.

![[Pasted image 20250831113024.png]]
5에서, 클라이언트가 충돌을 해소한 후에 충돌 해소를 서버에 기록한다.

**충돌 감지**
X가 Y의 이전 버전인지 확인하려면, 모든 구성요소가 같거나 작은 값을 가져야 함.
DX([s0, 1], [s1, 1]) < DY([s0, 1], [s1, 2])

같은 서버가 보낸 것 중에, 작은 값이 있다면 충돌이 발생한 것
DX([s0, 1], [s1, 2]) <> DY([s0, 2], [s1, 1])

단점
- 클라 로직 복잡
- 순서쌍 굉장히 빨리 늘어남
	- 오래된 순서쌍을 제거
	- 근데 아마존도 괜찮다고 함 ㅋ. 니네는 신경 쓰지 말 것

### 가십 프로토콜
![[Pasted image 20250831114323.png]]
- 주기적으로 자기 카운터 증가시킴

### 일시적 장애 처리
엄격한 정족수를 유지한다면, 읽기/쓰기 금지해야 한다.

**느슨한 정족수**
장애 상태인 서버를 정족수에서 무시하고,
장애가 일어나지 않은 서버가 이를 맡아서 처리한다.
맡아서 대신 처리한 서버는 서버가 복구되었을 때, 데이터를 인계한다.


![[Pasted image 20250831114646.png]]
s2에 보내진 요청은 s3가 맡아서 처리하고, s2가 복구되면 s3가 s2에 데이터를 인계한다.
