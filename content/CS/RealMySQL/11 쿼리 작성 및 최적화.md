## 11.4.2 WHERE 절과 GROUP BY 절, ORDER BY절의 인덱스 사용
### 11.4.2.1 인덱스를 사용하기 위한 기본규칙
**WHERE, ORDER BY, GROUP BY 가 인덱스를 사용하려면 
인덱스 칼럼의 값 자체를 변환하지 않고 사용해야 한다**. 
(B-Tree에 값 그대로 저장되어 있기 때문에)


```sql
# 값을 그대로 사용하지 않음
SELECT * FROM salaries WHERE salary * 10 > 150000
# 값을 그대로 사용
SELECT * FROM salaries WHERE salary > 150000/10
```
식을 조금만 변형하면 값을 그대로 사용할 수 있다.

어쩔 수 없다면, 미리 계산된 값을 저장하도록, 가상 컬럼, 함수 기반의 인덱스를 사용하면 된다.

**WHERE 절에 사용되는 비교 조건에서 양 쪽 모두 같은 데이터 타입이어야 한다.**

### 11.4.2.3 GROUP BY 절의 인덱스 사용

- 뒤 쪽에 있는 칼럼은 GROUP BY 절에 명시되지 않아도, 인덱스를 사용할 수 있다.

- GROUP BY에 명시된 칼럼이 하나라도 없으면, 전혀 인덱스를 이용하지 못한다.

## 11.4.8 GROUP BY (그룹핑)

- `GROUP BY` 절은 **쿼리 결과를 특정 컬럼 값에 따라 그룹으로 묶는 데 사용**됩니다,.
- 주로 `COUNT`, `MIN`, `MAX`, `AVG`, `SUM` 등과 같은 집계 함수를 그룹으로 묶인 결과에 적용하여 레코드를 컬럼으로 변환하는 데 활용됩니다.
- `GROUP BY` 절은 인덱스를 사용하여 빠르게 처리될 수 있습니다,.
    - `GROUP BY` 절에 명시된 컬럼은 **인덱스 컬럼의 순서 및 위치와 같아야 인덱스를 사용할 수 있습니다**,.
    - 인덱스를 구성하는 컬럼 중 뒤쪽에 있는 컬럼이 `GROUP BY` 절에 명시되지 않아도 인덱스를 사용할 수 있습니다.
    - `GROUP BY` 절에 명시된 컬럼 중 **하나라도 인덱스에 포함되지 않으면 해당 `GROUP BY` 절은 인덱스를 전혀 사용할 수 없습니다**,.
    - `WHERE` 절과는 달리, `GROUP BY` 절은 명시된 컬럼들의 순서가 바뀌면 인덱스를 사용할 수 없습니다.
- `GROUP BY`와 `ORDER BY` 절이 함께 사용될 경우, 둘 중 하나라도 인덱스를 사용하지 못하면 둘 다 인덱스를 사용하지 못합니다.
    - 둘 다 인덱스를 사용하려면, 두 절에 명시된 컬럼과 그 순서가 모두 같아야 합니다.
- **MySQL 8.0 버전부터는 `GROUP BY` 절이 컬럼의 정렬까지 함께 수행하는 기본 동작 방식이 변경되어, `GROUP BY`는 더 이상 결과의 정렬을 보장하지 않습니다**.

## 11.4.9 ORDER BY (정렬)

- `ORDER BY` 절은 **쿼리 결과 집합을 지정된 컬럼의 값에 따라 정렬하는 데 사용**됩니다,.
- `ORDER BY` 절도 인덱스를 사용하여 빠르게 처리될 수 있습니다,.
    - **`ORDER BY` 절의 모든 컬럼이 오름차순(`ASC`) 또는 내림차순(`DESC`) 중 한 가지 방향으로만 정렬될 때 인덱스를 사용할 수 있었습니다** (MySQL 8.0 이전).
    - **MySQL 8.0부터는 인덱스 생성 시 오름차순과 내림차순을 혼합하여 정의할 수 있게 개선되었습니다**.
    - `ORDER BY` 절의 컬럼들은 **인덱스에 정의된 컬럼의 왼쪽부터 일치해야 합니다**. 인덱스의 모든 컬럼이 `ORDER BY` 절에 사용될 필요는 없습니다.
- `ORDER BY` 절이 인덱스를 사용하지 못하는 경우에는 별도의 정렬 처리 과정(`filesort`)이 수행됩니다.
    - 쿼리 실행 계획의 `Extra` 컬럼에 "`Using filesort`" 코멘트가 표시됩니다.
    - 정렬 대상 레코드가 많은 경우 메모리 또는 디스크를 사용하여 정렬 작업이 이루어질 수 있습니다. `filesort` 단어에 포함된 'file'은 디스크 파일을 의미하는 것이 아니라 명시적인 정렬 알고리즘 수행을 의미합니다.
- `WHERE` 절과 `ORDER BY` 절이 함께 사용될 때 인덱스 사용 규칙:
    - **`WHERE` 절에서 동등 비교(`=`)로 사용된 컬럼과 `ORDER BY` 절에 명시된 컬럼이 인덱스를 구성하는 컬럼과 같은 순서로 연속해서 사용되었는지 확인**해야 합니다.
```mysql
index (column1, column2)
select * from table where column1 = "text" 
order by column2 ASC;
>> 아래처럼 변경됨.
select * from table where column1 = "text" 
order by column1 ASC, column2 ASC;

```
- `WHERE` 절의 동등 비교 조건으로 사용된 컬럼과 `ORDER BY` 절의 컬럼이 인덱스 컬럼의 왼쪽부터 일치해야 인덱스를 사용할 수 있습니다.
- `WHERE` 절의 동등 비교 조건으로 사용된 컬럼과 `ORDER BY` 절의 컬럼 사이에 인덱스 컬럼이 빠지는 부분이 있다면, `WHERE` 절이나 `ORDER BY` 절 모두 해당 인덱스를 효과적으로 사용하지 못할 수 있습니다. 이 경우 주로 `WHERE` 절만 인덱스를 이용할 수 있습니다.
- **MySQL의 기본 SQL 모드에서 큰따옴표(`"`)는 문자열 리터럴을 표현하는 데 사용되므로, `ORDER BY` 절에서 컬럼 이름을 큰따옴표로 묶으면 문자열 리터럴 값으로 정렬하라는 의미가 됩니다**. 식별자(컬럼 이름 등)는 역따옴표(`` ` ``)로 묶어야 합니다,.

## 11.4.10 서브쿼리 (Subquery)

- 서브쿼리는 **다른 SQL 문장 안에 포함된 쿼리**를 의미합니다,.
- 서브쿼리는 결과를 반환하는 형태에 따라 분류될 수 있습니다:
    - **스칼라 서브쿼리 (Scalar subquery):** 단일 행과 단일 컬럼을 반환합니다. `SELECT`, `WHERE`, `HAVING` 절 등 다양한 위치에 사용될 수 있습니다. `SELECT` 절의 서브쿼리는 반드시 스칼라 서브쿼리여야 합니다.
    - **로우 서브쿼리 (Row subquery):** 단일 행을 반환하지만 여러 컬럼을 반환할 수 있습니다. 주로 `WHERE` 또는 `HAVING` 절에서 비교 조건과 함께 사용됩니다. `SELECT` 절에서는 사용할 수 없습니다.
    - **테이블 서브쿼리 (Table subquery):** 여러 행과 여러 컬럼을 반환합니다. 주로 `FROM` 절이나 `WHERE` 절에서 사용됩니다.
- 서브쿼리 사용 예시 및 특징:
    - **`IN (subquery)`:** `WHERE` 절에서 서브쿼리 결과 집합에 값이 포함되는지 여부를 확인합니다.
        - **MySQL 8.0 버전부터는 옵티마이저가 `IN (subquery)` 형태를 세미 조인 최적화(Semi Join Optimization)를 이용하여 더 빠른 쿼리로 변환하여 실행합니다**,,,.
        - 세미 조인 최적화에는 테이블 풀-아웃, 퍼스트 매치, 루스 스캔, Materialization, 중복 제거 등의 전략이 있습니다.
        - `NOT IN` 연산자는 부정형 비교이기 때문에 인덱스를 이용해 처리 범위를 줄이는 조건으로는 사용하기 어렵습니다.
    - **`FROM` 절에 사용된 서브쿼리:** 인라인 뷰(Inline View) 또는 파생 테이블(Derived Table)로 간주됩니다.
        - 이전 버전의 MySQL에서는 `FROM` 절의 서브쿼리 결과를 항상 임시 테이블로 저장했지만, **MySQL 5.7 버전부터는 옵티마이저가 `FROM` 절의 서브쿼리를 외부 쿼리로 병합하는 최적화를 수행하도록 개선되었습니다**.
- MySQL 8.0 버전부터는 래터럴 조인(Lateral JOIN) 이나 윈도우 함수(Window Function)와 같은 새로운 기능을 통해 이전에는 서브쿼리나 스토어드 함수의 도움 없이 단일 SQL 문장으로 구현하기 어려웠던 기능들을 구현할 수 있게 되었습니다,.

## 11.7.4 테이블 변경

### 11.7.4.1 테이블 생성
![[Pasted image 20250608195357.png]]
- `TEMPORARY` 해당 데이터베이스 커넥션에서만 사용 가능한 임시 테이블을 생성
- `IF NOT EXIST` 이미 있을 때, 에러 무시
- `ENGINE` 엔진 선택
- `칼럼명 + 칼럼타입 + [타입별 옵션] + [NULL 여부] + [기본값]`
	- 문자열 타입은 반드시 칼럼이 최대한으로 저장할 수 있는 문자 수를 명시해야 한다.
	- 숫자 타입은 선택적으로 길이를 가질 수 있지만, 이는 실제 칼럼에 저장될 값의 길이를 의미하는 것이 아니라, 보여줄 길이를 지정하는 것이다.
	- `UNSIGNED` 양수만 가짐
	- `ZEROFILL` 숫자 값의 왼쪽에 0을 패딩함
	- DATE, DATETIME 은 5.5 부터 기본값을 현재 시간으로 명시할 수 있다.
	- `ENUM` 은 가질 수 있는 값을 정의해야 한다.

### 11.7.4.3 테이블 구조 변경
`ALTER TABLE` 명령을 사용한다. 

``` mysql
ALTER TABLE employees
        CONVERT TO CHARACTER SET UTF8MB4 COLLATE UTF8MB4_GENERAL_CI,
        ALGORITHM=INPLACE, LOCK=NONE;
```

- 기본 문자 집합과 콜레이션을 변경하는 명령
- 테이블의 모든 칼럼과 기존 데이터까지 모두 UTF8MB4 문자 셋의 콜레이션까지 UTF8MB4_GENERAL_CI로 변경한다


``` mysql
ALTER TABLE employees ENGINE=InnoDB,
        ALGORITHM=INPLACE, LOCK=NONE;
```

- 테이블을 스토리지 엔진을 변경하는 명령이다.
- 항상 테이블의 모든 레코드를 복사하는 작업이 필요하다.
	- ALTER 명령에 명시된 ENGINE이 기존과 동일하더라도 
	  테이블의 데이터를 복사하는 작업은 실행되기 때문에 주의해야 한다.
	- 테이블 데이터를 리빌드하는 목적으로도 사용된다.
	- 데이터가 저장되지 않는 빈 공간을 제거해 디스크 사용 공간을 줄이는 역할을 한다.

### 11.7.4.4 테이블 명 변경

`RENAME TABLE` 테이블 명 변경 및 다른 데이터베이스로 테이블을 이동할 때도 사용할 수 있다.
``` mysql
RENAME TABLE table1 TO table2;
```
- 이름만 변경하는 작업은 메타 정보만 변경하기 때문에 매우 빠르게 처리된다.
```mysql
RENAME TABLE db1.table1 TO db2.table2;
```
- 하지만 데이터베이스를 변경하는 경우에는 메타 정보뿐 아니라, 저장된 파일까지 이동해야 한다.
- 서로 다른 운영체제의 파일 시스템을 사용하고 있었다면, 파일의 크기에 비례해서 시간이 소요될 것이다.


```mysql
RENAME TABLE batch     TO  batch_old
			 batch_new TO  batch
```
- 일정 주기로 테이블을 교체할 때, 실행 중간에 batch테이블이 사라지는걸 방지함
- 명시된 모든 테이블에 잠금을 걸고, 이름 변경 실행
- 잠금 대기가 발생하지만, 에러가 발생하지는 않는다.

## 11.7.5 칼럼 변경

### 11.7.5.1 칼럼 추가
``` mysql
-- // 테이블의 제일 마지막에 새로운 칼럼을 추가
ALTER TABLE employees ADD COLUMN emp_telno VARCHAR(20),
       ALGORITHM=INSTANT;
```

마지막에 새로운 칼럼을 추가하므로 즉시 추가가 가능

``` mysql
-- // 테이블의 중간에 새로운 칼럼을 추가
ALTER TABLE employees ADD COLUMN emp_telno VARCHAR(20) AFTER emp_no,
       ALGORITHM=INPLACE, LOCK=NONE;
```

중간에 추가하는 경우, 테이블의 리빌드가 필요하다.
그래서 테이블이 큰 경우라면, 가능하다면 칼럼을 마지막 칼럼으로 추가하는 것이 좋다.

### 11.7.5.2 칼럼 삭제
```mysql
ALTER TABLE employees DROP COLUMN emp_telno,
	ALGORITHM=INPLACE, LOCK=NONE
```
항상 테이블의 리빌드를 필요로 한다.
즉, INSTANT는 쓸 수 없다.

### 11.7.5.3 칼럼 이름 및 칼럼 타입 변경
``` mysql
-- // 칼럼의 이름 변경
mysql> ALTER TABLE salaries CHANGE to_date end_date DATE NOT NULL,
       ALGORITHM=INPLACE, LOCK=NONE;
```

INPLACE를 사용하지만 리빌드는 필요하지 않다.

``` mysql
-- // INT 칼럼을 VARCHAR 타입으로 변경
mysql> ALTER TABLE salaries MODIFY salary VARCHAR(20),
       ALGORITHM=COPY, LOCK=SHARED;
```

COPY 알고리즘이 필요하고, 스키마 변경 도중 쓰기 작업이 불가능하다.

``` mysql
-- // VARCHAR 타입의 길이 확장
mysql> ALTER TABLE employees MODIFY last_name VARCHAR(30) NOT NULL,
       ALGORITHM=INPLACE, LOCK=NONE;
```

현재 길이와 확장 길이의 관계에 따라 리빌드가 필요할 수도 있고, 필요하지 않을 수도 있다.

```mysql
-- // VARCHAR 타입의 길이 축소
mysql> ALTER TABLE employees MODIFY last_name varchar(10) NOT NULL
       ALGORITHM=COPY, LOCK=SHARED;
```

해당 테이블의 데이터 변경은 허용하지 않으므로, SHARED 락이 필요하다

- VARCHAR, VARBINARY의 경우 최대 허용 사이즈는 메타데이터에 저장되지만, 
  실제 칼럼이 가지는 값의 길이는 데이터 레코드의 칼럼 헤더에 저장된다.
- 255 이하인 경우 1 바이트만 사용하고, 256 이상일 경우 2바이트를 사용한다.
- VARCHAR(10) >> VARCHAR(20) 의 경우에는 리빌드가 필요없다.
- VARCHAR(10) >> VARCHAR(64) 의 경우에는 리빌드가 필요하다.
	- UTF8MB4 문자 셋은 한 글자가 최대 4바이트를 사용할 수 있다.
	- 그러므로 VARCHAR(64) 는 최대 256바이트를 사용할 수 있다.
	- 그래서 1바이트에서 2바이트로 변경해야 하므로 테이블 레코드 전체를 다시 리빌드해야 한다.


# 11.7.6 인덱스 변경
`USING HASH` 는 MySQL Cluster (NDB)를 위한 옵션이다.
전문 검색 인덱스와 공간 검색 인덱스를 제외하면 전부 B-TREE 인덱스이다.
### 11.7.6.1 인덱스 변경
![[Pasted image 20250608210056.png]]
다음은 11.7.6 "인덱스 변경"에 대한 요약입니다.

MySQL 8.0에서는 대부분의 인덱스 변경 작업이 온라인 DDL로 처리 가능합니다. `USING BTREE` 또는 `USING HASH`와 같은 옵션은 MySQL Cluster를 위한 것이며, InnoDB나 MyISAM 스토리지 엔진에는 해당되지 않습니다.

### 11.7.6.1 인덱스 추가

- 인덱스 추가
    
```mysql 
mysql> ALTER TABLE employees ADD PRIMARY KEY (emp_no),
	   ALGORITHM=INPLACE, LOCK=NONE;
mysql> ALTER TABLE employees ADD UNIQUE INDEX ux_empno (emp_no),
	   ALGORITHM=INPLACE, LOCK=NONE;
mysql> ALTER TABLE employees ADD INDEX ix_lastname (last_name),
	   ALGORITHM=INPLACE, LOCK=NONE;
```
    
 **INPLACE 알고리즘과 `LOCK=NONE` 옵션으로 온라인 인덱스 생성이 가능**
    
    
- **FULLTEXT INDEX 및 SPATIAL INDEX 추가**
    
```mysql
mysql> ALTER TABLE employees 
	ADD FULLTEXT INDEX fx_firstname_lastname (first_name, last_name),
	ALGORITHM=INPLACE, LOCK=SHARED;
mysql> ALTER TABLE employees
	ADD SPATIAL INDEX fx_loc (last_location),
	ALGORITHM=INPLACE, LOCK=SHARED;
```

전문 검색 및 공간 검색 인덱스는 **INPLACE 알고리즘으로 생성이 가능하지만 `LOCK=SHARED` 잠금**
    

### 11.7.6.2 인덱스 조회
![[Pasted image 20250608211903.png]]
인덱스 목록을 조회할 때는 `SHOW INDEX` 명령이나 `SHOW CREATE TABLE` 명령

- Seq_in_index 인덱스에서 해당 컬럼의 위치 표시
	- 단일 컬럼 : 1
	- 복합 칼럼 : 2,3,4,5,...
- Cardianlity
	- 인덱스에서 해당 컬럼까지의 유니크한 값의 개수
	- 조합으로 따져서 표시
- `SHOW CREATE TABLE`은 간단하게 파악하기 좋음

### 11.7.6.3 인덱스 이름 변경

- **인덱스 이름 변경**

``` mysql
mysql> ALTER TABLE salaries RENAME INDEX ix_salary TO ix_salary2,
	   ALGORITHM=INPLACE, LOCK=NONE;
```
    
- 인덱스 이름 변경은 **INPLACE 알고리즘을 사용하며, 실제 데이터 리빌드 작업은 필요하지 않음** 
- 응용 프로그램에서 힌트로 사용하던 인덱스를 서비스 중단 없이 교체

- **인덱스 교체 예시**: 기존 인덱스를 삭제하고 새로운 인덱스로 교체하는 과정은 다음과 같습니다:

``` mysql
-- // 새 인덱스를 임시 이름(`index_new`)으로 생성
mysql> ALTER TABLE employees
	   ADD INDEX index_new (first_name, last_name),
	   ALGORITHM=INPLACE, LOCK=NONE;
```

``` mysql
-- // 기존 인덱스(`ix_firstname`)를 삭제
mysql> ALTER TABLE employees
   DROP INDEX ix_firstname,
-- // 동시에 새로 생성한 인덱스(`index_new`)의 이름을 기존 인덱스 이름으로 변경
   RENAME INDEX index_new TO ix_firstname,
   ALGORITHM=INPLACE, LOCK=NONE;
```

이 전체 과정은 **INPLACE 알고리즘으로 잠금 없이 온라인으로 처리됩니다**.

### 11.7.6.4 인덱스 가시성 변경

인덱스의 가시성을 변경하면, **서버가 쿼리를 실행할 때, 해당 인덱스를 사용할 수 있게 할지 말지**를 결정

- **인덱스를 보이지 않게/다시 보이게 변경**
``` mysql
mysql> ALTER TABLE employees ALTER INDEX ix_firstname INVISIBLE;
mysql> ALTER TABLE employees ALTER INDEX ix_firstname VISIBLE;
```

- 인덱스를 INVISIBLE 상태로 변경하면, **없는 것으로 간주하고 실행 계획을 수립한다**.

- **INVISIBLE >> 모니터링 >> 인덱스 삭제** 로 안전하게 인덱스를 삭제할 수 있게 되었다.

- 최초 인덱스 생성 시에도 `INVISIBLE` 속성을 부여할 수 있습니다. 

> [!info] `use invisible_indexes`
> MySQL 서버의 `optimizer_switch` 시스템 변수 중 
> `use_invisible_indexes` 옵션이 `ON`으로 설정된 경우, 
> 옵티마이저는 `INVISIBLE` 인덱스도 사용할 수 있지만, 
> 이 옵션의 기본값은 `OFF`입니다.


### 11.7.6.5 인덱스 삭제

- **세컨더리 인덱스 삭제**

``` mysql
mysql> ALTER TABLE employees DROP INDEX ux_empno, ALGORITHM=INPLACE, LOCK=NONE;
mysql> ALTER TABLE employees DROP INDEX fx_loc, ALGORITHM=INPLACE, LOCK=NONE;
```

세컨더리 인덱스 삭제는 일반적으로 매우 빠르게 처리되며,
**INPLACE 알고리즘을 사용하지만 실제 테이블 리빌드는 필요로 하지 않습니다**.

- **PRIMARY KEY 삭제**

``` mysql
mysql> ALTER TABLE employees DROP PRIMARY KEY, ALGORITHM=COPY, LOCK=SHARED;
```

프라이머리 키 삭제는 **모든 세컨더리 인덱스의 리프 노드에 저장된 프라이머리 키 값을 삭제해야 하므로,
임시 테이블로 레코드를 복사하여 테이블을 재구축(리빌드)해야 합니다**. 
이 작업은 **COPY 알고리즘을 사용하며, 레코드 쓰기가 불가능한 `SHARED` 모드의 잠금이 필요합니다**.
