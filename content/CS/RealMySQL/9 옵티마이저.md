# 옵티마이저
## 쿼리 실행 절차
1. SQL 파싱; 파스 트리
2. 테이블, 인덱스 선택
3. 데이터 가져오기


> [!info] 테이블 및 인덱스 선택에서는..
> - 불필요한 조건 제거 및 복잡한 연산 단순화
> - 여러 테이블 조인의 경우, 읽을 순서 결정
> - 각 테이블에 사용된 조건과 인덱스 통계 정보를 이용해 인덱스 결정
> - 임시 테이블에 넣고 다시 한번 가공해야 하는지 결정

# 기본 데이터 처리
### 풀 테이블 스캔
인덱스를 사용하지 않고 처음부터 끝까지
- 테이블 레코드 너무 작은 경우
- 인덱스 사용이 불가능할 경우
- 인덱스 레인지 스캔을 쓸 수 있어도, 너무 많은 경우

백그라운드 + 포그라운드 스레드가 처리하면서 꽤 빠르게 실행된다. (read_ahead)
- 풀 인덱스 스캔에서도 동일하게 사용된다.


# 정렬 (order by) (filesort)
### 인덱스 이용
+ +) 순서대로 읽기만 하면 됨. 빠름
+ -) CUD시에 부가적인 인덱스 추가/삭제가 필요,
+ -) 인덱스때문에 공간 더 필요, 메모리 필요

### Filesort 이용
- +) 많지 않으면 충분히 빠르다. 인덱스 이용의 단점 = 파일소트 장점
- -) 정렬 작업이 쿼리 실행시 처리되므로 레코드 대상 건수가 많아질수록 쿼리의 응답 속도가 느리다.
### 소트 버퍼
- 소트 버퍼보다 정렬해야할 양이 더 많다면 문제 발생!
- 멀티 머지 : 쪼갬 > 정렬 > 기록 > 정렬 > ... > 완료!
- 소트 버퍼 크다고 좋은건 아님. 그냥저냥임
	- Disk IOPS를 줄일 수는 있다

### 정렬 알고리즘
- 투 패스 : 정렬 키 + 로우 ID
	- 두번 읽음
- 싱글 패스 : 정렬 키 + 레코드 전체(고정 사이즈)
	- 더 많은 공간 필요
- 싱글 패스 : 정렬 키 + 레코드 전체(가변 사이즈)
	- 더 많은 공간 필요
	- 

### 정렬 처리 방법
아래쪽일 수록 처리 속도 떨어짐
- 인덱스
	- Extra : 별도 표기 없음
	- 인덱스는 정렬되어 있기 때문에 그냥 가져온다.
- 조인에서 드라이빙 테이블만 정렬
	- Extra : Using filesort
	- 드라이빙 테이블을 정렬하고, 그 결과와 조인한다.
- 조인에서 조인 결과를 임시 테이블로 저장 후 정렬
	- Extra : Using temporary; Using filesort
	- 정렬 기준이 드리븐 테이블에 있는 경우에 조인 결과를 먼저 만들고
	  그 결과를 정렬한다.

**정렬 처리 방식의 성능 비교**
LIMIT을 써도, OrderBy나 GroupBy때문에 느려지는 경우가 자주 발생한다.
- 스트리밍 방식 
	- 첫 레코드 가져오는건 빠르다.
- 버퍼링 방식
	- OrderBy, GroupBy하면 스트리밍 불가능하다.
	- 스토리지 엔진에서 가져올 때 까지 기다려야 한다.
	- 스토리지 엔진 > 서버(가공) > 사용자

> [!info] JDBC에서
> - MySQL이 스트리밍해도, JDBC 라이브러리가 버퍼링을 한다.
> - 기본 작동 방식이 그렇기 때문에, 변경하여 처리할 수 있다.


인덱스를 이용한 정렬 처리만 스트리밍 할 수 있다.
**인덱스 처리로 유도하고, 안된다면 드라이빙 테이블만 정렬해도 되게끔 하는 것도 좋은 튜닝 방법!**

### 상태 변수
- Sort_merge_passes : 멀티 머지 처리 횟수
- Sort_range : 인덱스 레인지 스캔 검색 결과 정렬 작업 수
- Sort_scan : 풀 테이블 스캔에 대한 정렬 작업 수
- Sort_rows : 지금까지 정렬한 전체 레코드 건수


## GROUP BY 처리
- 인덱스
- 루스 인덱스
	- 인덱스로 스캔 > 그룹 키 발견 > 조회 > 그룹키 발견 > ... > 그룹 키 없음 > 완료!
- 임시 테이블

## DISTINCT 처리
- SELECT DISTINCT : 조합이 유니크한 것
- COUNT(DISTINCT ...) : 함수 인자 조합이 유니크한 것
	- 임시 테이블을 사용 (explain 에도 안나옴!)
	- 인덱스에 대해서 하면, 인덱스 풀 스캔이나 레인지 스캔으로 수행
### 내부 임시 테이블
- MySQL 엔진 외에는 볼 수 없음
- 만들 때 TempTable 스토리지 엔진을 사용함.
- 커지면, 디스크에 기록하는 방식으로 전환한다.
	- MMAP or InnoDB
	- 디스크 파일 생성 후 바로 삭제를 실행한다.
	- 사용하는 프로세스가 없으면 바로 삭제됨.

### MRR과 배치 키 액세스
- Multi-Range Read (DS-MRR; Disk Sweep Multi-Range Read)
- 드라이빙 레코드 1건 -> 드리븐 테이블 일치 찾음
	- 드라이빙 : 조인에서 제일 먼저 읽는 테이블
	- 드리븐 : 조인에서 드라이빙이 아닌 테이블
	- Nested Loop join
- 조인 처리 = Mysql 엔진, 실제 레코드 검색 & Read = 스토리지 엔진
	- 이런 방식으로는 조인을 스토리지 레벨(읽/쓰) 에서는 최적화 할 수 없다.
- **드라이빙 테이블을 읽어서 버퍼링하는 방식으로 최적화**
	- 즉시 조인하지 않고
	- 데이터 페이지에 정렬된 순서로 접근
- MRR을 응용해서 실행되는 조인 = **BKA**
	- 기본적으로 off, 부가적인 정렬 작업이 필요해 오히려 성능에 악영향
### 블록 네스티드 루프 조인 (block_nested_loop)
- 조인의 연결 조건이 되는 칼럼에 모두 인덱스가 있는 경우에 사용되는 조인
- 중첩 for문 같다고 함
	- A 인덱스 1개 에 대해서 B인덱스 여러개를 찾아보기 때문 
- 순서가 반대인 것처럼 조인한다.
### 인덱스 컨디션 푸시다운
- 인덱스가 생성되어있는 필터링 조건인 경우, 인덱스를 이용해서 필터링한다.
	- 스토리지 엔진 레벨에서 필터링 가능
### 인덱스 확장
- use_index_extensions
- 세컨더리 인덱스에 자동으로 추가된 프라이머리 키를 활용할 수 있게 한다.
- 프라이머리 키를 식별자로 사용하는 MySql은 세컨더리 인덱스에도 프라이머리 키가 쓰여 있다.
- 숨은 프라이머리 키를 이용한다.
### 인덱스 머지
- 2개 이상의 인덱스를 이용해 쿼리를 처리한다
- 교집합
	- 두 개 이상의 인덱스가 AND로 연결되어 있는 경우에 교집합만 가져옴
	- 근데, 세컨더리 키에 프라이머리 키가 포함되어 있음 (인덱스 확장)
- 합집합
	- 두 개 이상의 인덱스가 OR로 연결되어 있는 경우에 합집합만 가져옴
	- 프라이머리 키를 이용한 우선순위 큐를 사용해서 합집합의 중복을 제거함
- 정렬 후 합집합
	- 두 개 이상의 인덱스가 OR로 연결되어 있는데, 각 인덱스로 쿼리했을 때의 정렬이 다를 때,
	- 정렬 한 후에 프라이머리 키를 이용한 우선순위 큐를 사용해서 합집합을 만듬.
### 세미조인
- 세미조인 : 다른 테이블에서 조건에 일치하는 레코드가 있는지 없는지만 체크하는 형태의 쿼리
- 세미 조인 최적화
	- Table Pull-out : 항상 켜짐
	- Duplicate Weed-out, Materialization : 사용 여부 선택 가능
	- First Match, Loose Scan : 사용 여부 결정 가능
### 테이블 풀-아웃
- 세미조인 서브쿼리를 아우터 쿼리로 끄집어낸 후에 쿼리를 조인 쿼리로 재작성
	- select * from where (select)
	- >> select * from join
- EXPLAIN 이후 SHOW WARNINGS 명령으로 재작성 쿼리를 살펴 볼 수 있음.
	- 사용 제한사항이 몇 가지 있음
	- 중요한 제한사항 : 서브쿼리 부분이 UNQ 인텍스나, PK 룩업으로 결과가 1건인 경우에만 사용 가능
### First Match
- In(subquery)를 EXIST(subquery)로 튜닝한 것과 비슷한 방법
	- select * from in (SUBQ)
	- select * from exist in subQ
- 있으면(exist) 바로 반환하고, 다른 인덱스를 뒤지지 않음.(first match)
	- 1건
### Loose scan
- 루스 인덱스 스캔과 비슷한 읽기 방식을 사용한다.
### Materialization
- 임시 테이블을 만들어서 그거랑 조인한다.
- 조건이 서브쿼리에만 있는 경우에 사용
- **select * from** where (sub_q)

### Duplicate Weedout
- Inner join으로 쿼리한 이후에, 중복을 제거
### 컨디션 팬아웃
- 옵티마이저가 실행 계획을 수립할 때, WHERE 조건절에 있는 칼럼에 대한 비율을 계산할 수 있다.
- 인덱스나 히스토그램이 있는 경우에 계산할 수 있다.
- 실행 계획 수립에 더 많은 자원을 사용한다.
### 파생 테이블 머지
- 임시테이블을 생성하는 서브 쿼리를 외부 쿼리로 병합
### 인비저블 인덱스
- 인덱스 가용상태를 변경할 수 있다.
- 한 쿼리에서도 인덱스를 타지 못하게 막을 수 있음
- 옵티마이저 레벨에서 수행할 수 있고,
- 직접 수행할 수 도 있다.
### 스킵 스캔
- 복합 인덱스의 순서가 중요하다.
- 후행 인덱스의 조건만으로 쿼리가 작성될 경우에 명시하지 않은 선행 인덱스 몇 개를 추가해서 쿼리한다.
