MySQL에서 **프로시저**, **함수**, **트리거**, **이벤트** 등 절차적 처리를 위한 기능들을 통칭하여 “스토어드 프로그램”이라 합니다. 이들은 동일한 문법 체계를 공유하며, 이 장에서는 **권한**, **보안**, **예외 처리** 등 핵심 요소에 중점을 둡니다.

# 14.1 스토어드 프로그램의 장단점
애플리케이션 로직을 대체할 것인지, 어떤 기능에 사용할지를 충분히 고려해야 하며, 
장단점을 파악해 **효율적인 사용 시점**을 판단하는 것이 중요합니다.

#### **✅ 장점**
- **보안 강화**: SQL 인젝션 방어에 효과적
- **공통 로직 재사용**: 코드 중복 제거
- **네트워크 효율**: 클라이언트-서버 간 왕복 횟수 감소
- **개발 책임 분리**: 애플리케이션 vs 데이터베이스 코드 분업

#### **⚠️ 단점**
- **낮은 실행 성능**: MySQL 엔진이 직접 해석/실행
- **파싱 비용**: 실행할 때마다 코드 파싱 발생
- **복잡한 유지보수**: 로직이 분산되어 설치, 배포, 유지보수 어려움

# 14.2 스토어드 프로그램 문법
- **헤더(정의부)**: 이름, 파라미터, 보안/옵션 포함
- **본문(바디)**: 실제 실행할 SQL 로직 기술
- 프로시저/함수/트리거/이벤트는 **헤더는 각기 다르지만, 본문은 동일한 문법**을 사용

## 14.2.1 예제 테스트 시 주의사항
- **MySQL 설정 필요**: 스택 공간 부족, 문법 오류 등 발생 가능
- **공백 인식 주의**: IGNORE_SPACES SQL 모드에서 함수명과 괄호 사이 공백 오류 발생 가능

## 14.2.2 스토어드 프로시저 (PROCEDURE)

- **RETURN 사용 불가**
- **IN, OUT, INOUT** 파라미터 지원
- MySQL 8.0부터:
    - **래터럴 조인**, **윈도우 함수** 등 고급 기능 사용 가능

## 14.2.3 스토어드 함수 (FUNCTION)
- **항상 값을 반환**
- SQL 문장 내에서 직접 호출 가능
- 제약이 많으며, **DETERMINISTIC 설정**이 성능에 영향

## 14.2.4 트리거 (TRIGGER)
- 테이블의 **INSERT, UPDATE, DELETE** 전후에 자동 실행
- OLD, NEW 객체를 통해 **변경 전후 값**에 접근 가능
- 필수는 아니며, **DDL 성능 저하** 유발 가능

## 14.2.5 이벤트 (EVENT)
- cron처럼 **정해진 시점/주기**에 SQL 실행
- **정기적 백업, 로그 정리** 등 배치 작업에 유용
- event_scheduler 시스템 변수를 통해 활성화

## 14.2.6 스토어드 프로그램 본문 
- 시작 : `BEGIN`
	- 스토어드 프로그램에서 트랜젹션 하려면 `START TRANSACTION` 사용해야 함.
- 끝 : `END`

### 트랜잭션

```mysql
mysql> CREATE PROCEDURE sp_hello ( IN name VARCHAR(50) )
    BEGIN
        START TRANSACTION;
        INSERT INTO tb_hello VALUES (name, CONCAT('Hello ',name));
        COMMIT;
    END;;
```

안에서 커밋할 지 밖에서 커밋할 지는 잘 생각해서 정해라.

스토어드 함수랑 트리거는 트랜잭션 커밋/롤백 못하므로, 외부에서 트랜잭션하는 경우만 있다.

    ELSEIF p_value2 IS NULL THEN

``` mysql
-- LOOP : 무한 루프
mysql> CREATE FUNCTION sf_factorial1(p_max INT)
RETURNS INT
BEGIN
    DECLARE v_factorial INT DEFAULT 1;

    factorial_loop : LOOP
        SET v_factorial = v_factorial * p_max;
        SET p_max = p_max - 1;
        IF p_max <= 1 THEN -- 조건
            LEAVE factorial_loop; -- LEAVE {레이블}
        END IF;
    END LOOP;

    RETURN v_factorial;
END;;

-- REPEAT : 조건 루프, 일단 한번은 실행
mysql> CREATE FUNCTION sf_factorial2(p_max INT)
RETURNS INT
BEGIN
    DECLARE v_factorial INT DEFAULT 1;
    REPEAT
        SET v_factorial = v_factorial * p_max;
        SET p_max = p_max - 1;
    UNTIL p_max <= 1 END REPEAT; -- 조건

    RETURN v_factorial;
END;;

-- WHILE : 처음에도 체크해서 0번 실행 가능
mysql> CREATE FUNCTION sf_factorial3(p_max INT)
RETURNS INT
BEGIN
    DECLARE v_factorial INT DEFAULT 1;

    WHILE p_max > 1 DO
        SET v_factorial = v_factorial * p_max;
        SET p_max = p_max - 1;
    END WHILE;

    RETURN v_factorial;
END;;
```

### 핸들러와 컨디션 - 에러 핸들링
**ERROR NO**
- MySQL에서만 유효한 에러 식별 번호          

**SQLSTATE**
- ANSI SQL 표준을 지원하는 DBMS에서는 모두 똑같은 값과 의미를 가진다.
- `HY000` : 매핑되지 않는 에러
- `00` 정상 처리
- `01` 경고 메시지
- `02` Not found (결과 없음)

**원인은 똑같은데, 번호가 다른 것들을 눈여겨 보아야 한다.**
그래서 핸들러에 매핑할 때, SQLSTATE를 사용하는게 좋다. (빠뜨리면 안되니까)


### 핸들러
``` mysql
DECLARE handler_type HANDLER
  FOR condition_value [, condition_value] ... handler_statements
```

**핸들러 타입**
- EXIT : 핸들링 이후 스토어드 프로그램 탈출, 종료
	- 그래서 핸들러랑 스토어드 함수랑 반환 타입 맞춰줘야 한다.
- CONTINUE : 핸들링 이후 스토어드 프로그램 계속 실행

**Condition_value**
- SQLSTATE : 스토어드 프로그램이 실행되는 도중 어떤 이벤트가 발생했을 때 해당 이벤트의 SQLSTATE 값이 일치할 때 실행
- SQLWARNING : 스토어드 프로그램에서 코드를 실행하던 중 경고(SQL Warning)가 발생했을 때 실행되는 핸들러를 정의.
	- SQLWARNING 키워드는 SQLSTATE 값이 `01`로 시작하는 이벤트를 의미한다.
- NOT FOUND : SELECT 쿼리 문의 결과 건수가 1건도 없거나 CURSOR의 레코드를 마지막까지 읽은 뒤에 실행하는 핸들러를 정의할 때 사용한다.
	- NOT FOUND 키워드는 SQLSTATE 값이 `02`로 시작하는 이벤트를 의미한다.
- SQLEXCEPTION : 경고(SQL Warning)와 NOT FOUND, 
	- `00`(정상 처리)로 시작하는 SQLSTATE 이외의 모든 케이스를 의미
- 직접 명시 : 코드 실행 중 어떤 이벤트가 발생했을 때 SQLSTATE 값이 아닌 MySQL의 에러 번호 값을 비교해서 실행되는 핸들러를 정의할 때 사용

``` mysql
DECLARE CONTINUE HANDLER FOR SQLEXCEPTION SET error_flag=1;
```

``` mysql
DECLARE EXIT HANDLER FOR SQLEXCEPTION
BEGIN
  ROLLBACK;
  -- 결과를 따로 사용하지 않는 쿼리는 즉시 클라이언트에게 전송됨.
  SELECT 'Error occurred - terminating';
END ;;
```

```mysql
-- ERROR_NO 이용
DECLARE CONTINUE HANDLER FOR 1022, 1062 SELECT 'Duplicate key in index';

-- SQLSTATE 이용
DECLARE CONTINUE HANDLER FOR SQLSTATE '23000' SELECT 'Duplicate key in index';
```
**커서를 반환(SELECT)하는 건 스토어드 프로시저에서만 가능**

```mysql
-- NOT FOUND 이용
DECLARE CONTINUE HANDLER FOR NOT FOUND SET process_done=1;

-- SQLSTATE 이용
DECLARE CONTINUE HANDLER FOR SQLSTATE '02000' SET process_done=1;

-- ERROR NO 이용
DECLARE CONTINUE HANDLER FOR 1329 SET process_done=1;
```
위 세 개는 같은 핸들러이다.

```mysql
DECLARE EXIT HANDLER FOR SQLWARNING, SQLEXCEPTION
BEGIN
  ROLLBACK;
  SELECT 'Process terminated, Because error';
  SHOW ERRORS;
  SHOW WARNINGS;
END;
```

```mysql
-- 옛날 방식
mysql> CREATE FUNCTION sf_divide_old_style (p_dividend INT, p_divisor INT)
    RETURNS INT
    BEGIN
        IF p_divisor IS NULL THEN

        ELSEIF p_divisor = 0 THEN

```

존재하지 않는 프로시저를 호출해서 에러를 발생시켰다.


``` mysql
mysql> CREATE FUNCTION sf_divide (p_dividend INT, p_divisor INT)
    RETURNS INT
    BEGIN
        DECLARE null_divisor CONDITION FOR SQLSTATE '45000';

        IF p_divisor IS NULL THEN
            SIGNAL null_divisor
                SET MESSAGE_TEXT='Divisor can not be null', MYSQL_ERRNO=9999;
        ELSEIF p_divisor=0 THEN
            SIGNAL SQLSTATE '45000'
                SET MESSAGE_TEXT='Divisor can not be 0', MYSQL_ERRNO=9998;
        ELSEIF p_dividend IS NULL THEN
            SIGNAL SQLSTATE '01000'
                SET MESSAGE_TEXT='Dividend is null, so regarding dividend as 0', MYSQL_ERRNO=9997;
            RETURN 0;
        END IF;

        RETURN FLOOR(p_dividend / p_divisor);
    END;;
```

- 첫번째
	- null_divisor 컨디션 참조
- 두번째
	- 직접 SQLSTATE '45000'
- 세번째
	- 경고 발생시킴
```mysql
mysql> CREATE PROCEDURE sp_remove_user (IN p_userid INT)
    BEGIN
        DECLARE v_affectedrowcount INT DEFAULT 0;
        DECLARE EXIT HANDLER FOR SQLEXCEPTION
        BEGIN
            SIGNAL SQLSTATE '45000'
                SET MESSAGE_TEXT='Can not remove user information', MYSQL_ERRNO=9999;
        END;

        -- // 사용자의 정보를 삭제
        DELETE FROM tb_user WHERE user_id = p_userid;
        -- // 위에서 실행된 DELETE 쿼리로 삭제된 레코드 건수를 확인
        SELECT ROW_COUNT() INTO v_affectedrowcount;
        -- // 삭제된 레코드 건수가 1건이 아닌 경우에는 에러 발생
        IF v_affectedrowcount <> 1 THEN
            SIGNAL SQLSTATE '45000';
        END IF;
    END;;
```


### 커서
(= JDBC ResultSet)
but 스토어드 프로그램의 커서는 JDBC, PHP의 결과보다 기능이 제한적임.
- 전진만 가능
- 커서 컬럼을 바로 업데이트할 수 없음

 **센서티브 커서 (Sensitive Cursor)**
- 실제 레코드에 대한 **포인터만 유지**함.
- **데이터 변경 및 삭제 가능**.
- **실시간 반영**됨 (레코드가 삭제되거나 조건 불일치 시 커서에서도 바로 반영).
- 임시 테이블 복사 없음 → **속도 빠름**.

**인센서티브 커서 (Insensitive Cursor)**
- 레코드를 **임시 테이블에 복사**해서 사용.
- **조회 전용** (변경/삭제 불가능).
- 복사 때문에 **속도 느림**, 하지만 **트랜잭션 충돌 없음**.

 **어센서티브 커서**
 - 인센서티브 커서랑 센서티브 커서를 혼용
 - 스토어드 프로그램에서 정의되는 커서

``` mysql
mysql> CREATE FUNCTION sf_emp_count(p_dept_no VARCHAR(10))
    RETURNS BIGINT
    BEGIN
        /* 사원 번호가 20000보다 큰 사원의 수를 누적하기 위한 변수 */
        DECLARE v_total_count INT DEFAULT 0;
        /* 커서에 더 읽어야 할 레코드가 남아 있는지 여부를 위한 플래그 변수 */
        DECLARE v_no_more_data TINYINT DEFAULT 0;
        /* 커서를 통해 SELECT된 사원 번호를 임시로 담아 둘 변수 */
        DECLARE v_emp_no INTEGER;
        /* 커서를 통해 SELECT된 사원의 입사 일자를 임시로 담아 둘 변수 */
        DECLARE v_from_date DATE;
        /* v_emp_list라는 이름으로 커서 정의 */
        DECLARE v_emp_list CURSOR FOR

        SELECT emp_no, from_date FROM dept_emp WHERE dept_no = p_dept_no;

        /* 커서로부터 더 읽을 데이터가 있는지를 나타내는 플래그 변경을 위한 핸들러 */
        DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_no_more_data = 1;

        /* 정의된 v_emp_list 커서를 오픈 */
        OPEN v_emp_list;
        REPEAT
            /* 커서로부터 레코드를 한 개씩 읽어서 변수에 저장 */
            FETCH v_emp_list INTO v_emp_no, v_from_date;
            IF v_emp_no > 20000 THEN
                SET v_total_count = v_total_count + 1;
            END IF;
        UNTIL v_no_more_data END REPEAT;

        /* v_emp_list 커서를 닫고 관련 자원을 반환 */
        CLOSE v_emp_list;

        RETURN v_total_count;
    END ;;
```

DECLARE로 정의하는 순서가 있다.
1. 로컬 변수와 CONDITION
2. CURSOR
3. HANDLER
