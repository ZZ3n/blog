- **16.1 개요 (Overview)**
    
    - 복제는 **소스 서버(Source Server)**의 데이터를 하나 이상의 **레플리카 서버(Replica Server)**로 동기화하는 것을 의미합니다.
    - 주요 활용 목적은 다음과 같습니다:
        - **스케일 아웃(Scale-out)**: 읽기 트래픽을 분산하여 DB 서버의 부하를 줄이는 데 사용됩니다.
        - **데이터 백업(Data Backup)**: 소스 서버의 성능에 영향을 주지 않고 레플리카 서버에서 백업을 수행합니다.
        - **데이터 분석(Data Analysis)**: 무거운 분석 쿼리를 레플리카 서버에서 실행하여 메인 서비스의 성능 저하를 방지합니다.
        - **지리적 분산(Geographic Distribution)**: 애플리케이션 서버와 가까운 위치에 레플리카 서버를 두어 통신 지연 시간을 줄이고 응답 속도를 개선합니다.
- **16.2 복제 아키텍처 (Replication Architecture)**
    
    - 복제 과정에서 레플리카 서버는 릴레이 로그(Relay Log)를 비롯한 세 가지 유형의 복제 관련 데이터를 생성하고 관리합니다.
    - 소스 서버에 문제가 발생하면 레플리카 서버의 I/O 스레드가 중단되지만, 레플리카 서버 자체는 여전히 쿼리를 처리할 수 있습니다. 단, 데이터는 동기화되지 않은 상태가 됩니다.
- **16.3 복제 타입 (Replication Type)**
    
    - **16.3.1 바이너리 로그 파일 위치 기반 복제 (Binary Log File Position Based Replication)**
        - MySQL 복제 기능이 처음 도입되었을 때부터 제공된 방식으로, 바이너리 로그 파일명과 파일 내 위치(Position)를 기반으로 이벤트를 식별합니다.
        - 복제 구성에 참여하는 각 MySQL 서버는 고유한 `server_id` 값을 가져야 합니다.
        - 이 방식은 장애 발생 시 복제 토폴로지 변경 및 장애 복구를 어렵게 만들 수 있습니다.
---
    - **16.3.2 글로벌 트랜잭션 아이디(GTID) 기반 복제 (GTID Based Replication)**
        - MySQL 5.6 버전부터 도입되었으며, 복제에 참여한 모든 MySQL 서버에서 **고유한 식별 값(GTID)**이 각 트랜잭션에 부여됩니다.
        - GTID를 사용하면 바이너리 로그 파일명과 위치를 추적할 필요가 없어 **장애 복구 및 토폴로지 변경이 훨씬 용이**해집니다.
        - `mysql.gtid_executed` 테이블에 적용된 GTID 셋 정보가 주기적으로 압축되어 관리됩니다.
        - `enforce_gtid_consistency`와 `gtid_mode` 시스템 변수를 통해 GTID 일관성을 제어할 수 있습니다.
## 16.3.2 글로벌 트랜잭션 아이디(GTID) 기반 복제

- 바이너리 로그 파일 위치 기반 복제
	- 레플리카마다 동일한 이벤트대해 서로 다른 식별값을 갖게 되는 문제가 있다.
		- 이벤트 식별자 = bin log 파일명 + 파일 내 위치 값 << 복제 서버마다 다른 값을 가짐
	- 복제 서버마다 호환되지 않는 정보로 인해, **복제 토폴로지 변경이 불가능**
		- 복제 참여 서버들 중 일부 장애가 있을 때 필요, failover가 어려움
		- 고가용성 솔루션에서는 복잡한 계산 or 포기

**만약 동일한 고유 식별값을 가진다면?**
- 손쉽게 복제 토폴로지 변경 가능
- 장애복구 소요 시간 감소

그래서 나온게 GTID
- 전체 참여 서버에서 고유하도록 각 이벤트에 부여된 식별 값

### 16.3.2.2 글로벌 트랜잭션 아이디
> **GTID**
- 서버에서 커밋된 각 트랜잭션과 연결된 고유 식별자
- 복제 토폴로지 내의 모든 서버에서 고유
- 커밋되어 바이너리 로그에 기록된 트랜잭션에 한해서만 할당됨
	- SELECT 나 sql_log_bin이 비활성화 돼 있는 상태에서 발생한건 GTID 없음

> GTID = \[source_id\]:\[transaction_id\]
- 소스 아이디는 트랜잭션이 발생된 소스 서버를 식별하기 위한 값
	- MySQL 서버의 server_uuid 시스템 변수를 사용
	- 서버 시작되면서 자동으로 부여, auto.cnf에 값이 있음
	- auto.cnf 까지 사용해서 새로운 레플리카를 구축하면 에러날 수 있음
- 트랜잭션 아이디는 커밋된 트랜잭션 순서대로 부여되는 값

>GTID 조회
- 테이블 gtid_executed 조회, 변수 gtid_executed 조회
- SHOW MASTER STATUS를 통해서 GTID 및 바이너리 로그 파일 및 위치 값 같이 확인 가능

> GTID 셋 (GTID Sets)
- 하나 이상의 GTID 값으로 이루어진 것
- `ed22da00-e052-11ea-ae88-ee4baf89a396:1-5:18:99-103`
- `8b20949a-da22-11ea-b0f8-44d14afe1f9d:1-2,ed22da00-e052-11ea-ae88-ee4baf89a396:1-5`
	- 여러 서버에서 복제해올 경우


![[Pasted image 20250706203413.png]]
> **gtid_executed TABLE** 
- 바이너리 로그가 비활성되어 있는 상태에서 gtid기반 복제를 사용할 수 있게 한다.
- 바이너리 로그가 손실되었을 때, gtid값이 보존될 수 있게 한다.
- 8.0.17 이상이면 트랜잭션 커밋될 때 마다, gtid 값이 바로 저장된다.
	- 8.0.17 미만이거나, InnoDB 엔진이 아니면, 바이너리 로그 파일이 로테이션되거나, 
	  mysql서버가 종료될 때만 gtid_executed에 저장된다.
	- 그럴 때는 시스템 변수 값 (gtid_executed)를 확인해야 한다.

![[Pasted image 20250706203448.png]]


> **gtid_executed TABLE** 압축
- 많이 쌓이면 전체 데이터를 하나로 압축한다.
	- 연속된 것들끼리 모아서 하나로 만듬
	- 바이너리 로그 활성화시, 로테이션 될 때 자동으로 압축
	- 바이너리 로그 비활성화시, `thread/sql/compress_gtid_table`이라는 포그라운드 스레드가 수행
		- gtid_executed_compression_period 시스템 변수에 도달하면 스레드에서 압축을 수행
			- 0이면 압축 안 하고, 필요에 따라 자동으로 수행

### 16.3.2.3 글로벌 트랜잭션 아이디 기반의 복제 구축
- GTID 활성화와 GTID 기반 복제를 사용하는 건 별개의 얘기

#### 16.3.2.3.1 설정 준비
> 소스 및 레플리카 설정
- gtid_mode=ON 과 enforce_gtid_consistency=ON을 꼭 함께 명시해야 한다.
	- 안 그러면 MySQL서버 기동하지 않는다.
- super 어드민은 레플리카에서도 DML, DDL할 수 있다.
	- 레플리카 서버에서 DML, DDL 하지 않게, super_read_only 설정도 하자.
	- 필요할 때, ON, OFF 하면 된다.

#### 16.3.2.3.2 복제 계정 준비
- 복제에서 사용할 계정 준비
- 소스 서버에서 실행

#### 16.3.2.3.3 데이터 복사
mysqldump를 사용해서 레플리카에 적재
```shell
mysqldump -uroot -p --single-transaction --master-data=2 --set-gtid-purged=ON \
  --opt --routines --triggers --hex-blob --all-databases > source_data.sql
```

덤프 시작 시점의 소스 서버 gtid 값을 레플리카 서버에서 다음 2개의 시스템 변수에 할당해야 한다.
- `gtid_executed`  :  서버에서 실행되어 바이너리 로그 파일에 기록된 모든 트랜잭션들의 GTID 셋
- `gtid_purged` : 현재 서버의 바이너리 로그 파일에 존재하지 않는 모든 트랜잭션들의 GTID 셋

MySQL설치하고 실행시키면, 위 두 값은 비어있는데, 그 때 gtid_purged에 값 설정하면 자동으로 들어감

만약 있으면, RESET MASTER를 실행해서 비워버리면 된다.
- 바이너리 로그 싹 날아가니까 주의

> --set-gtid-purged
![[Pasted image 20250706205104.png]]
- 덤프 시작 시점의 gtid가 덤프 파일에 기록
- sql_log_bin 시스템 변수 비활성화 구문도 기록
	- 레플리카에서 새로운 gtid 발급 방지
- 기본값 AUTO
- 그냥 마이그레이션 하는 경우에 OFF로 설정해야 함
	- 마이그레이션 된 서버에 연결된 레플리카가 데이터를 복제하지 않을 수 있음
 
```mysql
SET @@SESSION.SQL_LOG_BIN= 0;

--
-- GTID state at the beginning of the backup
--

SET @@GLOBAL.GTID_PURGED=/*!80000 '+'*/ 'ed22da00-e052-11ea-ae88-ee4baf89a396:1-30';
```
- --set-gtid-purged=ON
- '+' 는 값에 새로운 값 추가를 의미

### 16.3.2.4 글로벌 트랜잭션 아이디 기반 복제에서 트랜잭션 건너뛰기
바이너리 로그 위치 기반 복제에서는 sql_slave_skip_counter를 이용해서 문제 되는 이벤트 그룹을 건너뛰었다.

하지만, GTID에서는 그럴 수 없다.

자신과 소스 GTID 값을 비교해서 가져온다. 그러므로, 더 적거나, 더 많은 GTID값을 가진 채로 유지시킬 수가 없다.
무시하고 싶다면 **수동으로 빈 트랜잭션(더미 트랜잭션)을 생성해 GTID값을 만들어야 한다.**

![[Pasted image 20250706210451.png]]

- Auto_Position 이 1 인걸 보니, GTID 기반 복제이다.
- 중복 키 에러로 인해 멈추어 있다
- Retrieved_Gtid_Set, Executed_Gtid_Set 을 보니, 3-7을 가져왔고, 1-6이 실행되었다는 것을 알 수 있다.

> [!info] 왜 3-7만 있죠? 1-2는 어디갔죠?
> 1-2 는 백업을 통해 실행되어서 Retrieved_Gtid_Set에 없는 것

해결을 위해서 `:7`  트랜잭션을 레플리카 서버에서 무시하려면,
- 복제를 멈추고
- 빈 트랜잭션을 강제로 만들어서 바이너리 로그 스트림에 밀어넣으면 된다.

``` sql
-- // 복제 중단
mysql_Replica> STOP REPLICA;
Query OK, 0 rows affected (0.02 sec)

-- // gtid_next 변수 값을 문제가 발생한 트랜잭션의 GTID인
-- // "af995d80-939e-11eb-bb37-ba122a9a8ae3:7"로 설정
```

### 16.3.2.5 Non-GTID 기반 복제에서 GTID 기반 복제로 온라인 변경
5.7.6 이상부터 가능
그 이전에서는 MySQL 재시작해야함

`enforce_gtid_consistency`
- 소스와 레플리카 서버 간의 데이터 일관성을 해칠 수 있는 쿼리들이 실행되는 것을 허용하거나, 허용하지 않는다.
	- 트랜잭션 지원 테이블과, 트랜잭션 미지원 테이블을 함께 변경
	- CREATE TABLE ... SELECT .. 구문
	- 트랜잭션 내에서 CREATE TEMPORARY TABLE, DROP TEMPORARY TABLE 구문
- 소스에서 레플리카로 복제되어 적용될 때, 단일 트랜잭션으로 처리되지 않을 수 있다.
	- 하나가 아니라 개별 이벤트로 분류되면, 원자적으로 처리 불가
![[Pasted image 20250706211949.png]]

`gtid_mode`
- 바이너리 로그에 트랜잭션들이 GTID 기반으로 로깅될 수 있는지 여부
- 트랜잭션 유형별로 MySQL서버에서의 처리 가능 여부
![[Pasted image 20250706211937.png]]
- gtid_mode는 각 단계마다 한 단계씩 변경할 수 있다.
- 복제 그룹 내에서 변경하면 순차적으로 값 변경이 이루어진다.
	- 그래서 동시점에 다른 gtid_mode를 가진 서버가 있을 수 있으므로 호환성을 체크해야 한다.
![[Pasted image 20250706212144.png]]


>**Non-GTID 기반 복제 에서 GTID 활성화 후 GTID기반 복제로 변경**


각 서버에 **SET enforce_gtid_consistency = WARN**
- 모니터링

각 서버에 **SET enforce_gtid_consistency = ON**
- 별 일 없으면 ON

각 서버에 **SET GLOBAL gtid_mode = OFF_PERMISSIVE**
- 소스에서 신규 트랜잭션은 바이너리 로그에 익명 트랜잭션으로 기록
- 레플리카에서는 익명, GTID 트랜잭션 둘 다 처리할 수 있다.

각 서버에 **SET GLOBAL gtid_mode = ON_PERMISSIVE**
- 소스에서 신규 트랜잭션이 바이너리 로그에 GTID 트랜잭션으로 기록
- 레플리카에서는 둘 다 처리 가능

**잔여 익명 트랜잭션 확인**
![[Pasted image 20250706213244.png]]
- 레플리카 서버에서는 0이었다가 아니었다가 할 수 있는데, 0이 한번이라도 보이면 OK

**my.cnf 변경**
- gtid_mode=ON
- enforce_gtid_consistency=ON
- 재시작해도 유지되게끔 수정

**GTID 기반 복제를 사용하도록 복제 설정 변경**
- 더 이상 익명 트랜잭션은 생기지 않는다.
- 기존 바이너리 로그 위치 기반 복제도 GTID 기반의 복제로 변경할 수 있게 된다.
- 소스를 제외한 레플리카 서버에서 다음 명령어를 실행한다.
``` mysql
STOP REPLICA;
CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION=1;
START REPLICA;
```

### 16.3.2.6 GTID 기반 복제 제약 사항
- enforce_gtid_consistency=ON으로 인해 일부 유형 쿼리를 실행할 수 없다.
- sql_slave_skip_counter를 이용해서 복제된 트랜잭션을 건너뛸 수 없다.
- CHANGE REPLICATION SOURCE TO (또는 CHANGE MASTER TO) 구문의 IGNORE_SERVER_IDS 옵션은 더이상 사용되지 않는다.
	- 순환 복제 구조에서 한 서버가 장애로 제외되었을 때, 장애 서버에서 발생한 이벤트가 중복으로 적용되지 않게 할 때, 유용하게 사용할 수 있는데,
	- GTID 사용 레플리카 서버는 이미 적용된 트랜잭션을 식별 가능해서 필요없다.

- **16.4 복제 데이터 포맷 (Replication Data Format)**
    
    - **16.4.1 Statement 기반 바이너리 로그 포맷 (Statement Based Binary Log Format)**
        - 실행된 SQL 문장을 바이너리 로그에 기록합니다.
        - `NOW()`와 같은 비확정적(non-deterministic) 함수가 포함된 쿼리에서 소스-레플리카 간 데이터 불일치가 발생할 수 있습니다.
        - 트랜잭션 격리 수준이 `REPEATABLE-READ` 이상이어야 합니다.
    - **16.4.2 Row 기반 바이너리 로그 포맷 (Row Based Binary Log Format)**
        - 변경 전후의 데이터 자체(로우 이미지)를 바이너리 로그에 기록합니다.
        - 비확정적 쿼리에도 데이터 일관성을 보장합니다.
        - Statement 포맷보다 바이너리 로그 파일 크기가 커질 수 있습니다.
    - **16.4.3 Mixed 포맷 (Mixed Format)**
        - Statement와 Row 포맷을 혼합한 방식으로, 기본적으로 Statement를 사용하다가 Statement 방식으로 안전하지 않은 쿼리에 대해 자동으로 Row 포맷으로 전환하여 기록합니다.
    - **16.4.4 Row 포맷 용량 최적화 (Row Format Volume Optimization)**
        - **바이너리 로그 로우 이미지**: 변경된 로우 데이터를 저장하는 방식을 `FULL`, `NOBLOB`, `MINIMAL`로 설정하여 용량을 최적화할 수 있습니다.
        - **바이너리 로그 트랜잭션 압축**: 바이너리 로그에 기록되는 트랜잭션을 압축하여 용량과 네트워크 트래픽을 줄입니다. 이는 CPU 및 메모리 사용량을 증가시키고 처리 시간을 지연시킬 수 있습니다.
- **16.5 복제 동기화 방식 (Replication Synchronization Methods)**
    
    - **16.5.1 비동기 복제 (Asynchronous Replication)**
        - 소스 서버는 레플리카의 동기화 여부를 기다리지 않고 트랜잭션을 커밋합니다.
        - **장점**: 소스 서버의 트랜잭션 처리 속도가 빠르고, 레플리카 서버 문제에 영향을 받지 않습니다.
        - **단점**: 소스 서버 장애 시 데이터 유실 가능성이 있으며, 데이터 일관성을 보장하지 못합니다.
    - **16.5.2 반 동기 복제 (Semi-synchronous Replication)**
        - 소스 서버는 트랜잭션을 커밋하기 전에 최소 하나 이상의 레플리카 서버가 변경 이벤트를 릴레이 로그에 기록했음을 응답(ACK)할 때까지 기다립니다.
        - **장점**: 비동기 복제보다 **향상된 데이터 무결성을 제공**하며, 데이터 유실 위험을 줄입니다.
        - **단점**: 네트워크 왕복 시간으로 인해 트랜잭션 처리 속도가 비동기 방식보다 느려질 수 있습니다.
        - 설정된 타임아웃 시간 동안 응답이 없으면 자동으로 비동기 복제 방식으로 전환됩니다.
- **16.6 복제 토폴로지 (Replication Topology)**
    
    - **16.6.1 싱글 레플리카 복제 구성 (Single Replica Replication Configuration)**
        - 가장 기본적인 형태로, 하나의 소스 서버와 하나의 레플리카 서버로 구성됩니다.
        - 주로 **예비 서버 및 데이터 백업 수행** 용도로 사용됩니다.
    - **16.6.2 멀티 레플리카 복제 구성 (Multi Replica Replication Configuration)**
        - 하나의 소스 서버에 2개 이상의 레플리카 서버가 연결된 형태입니다.
        - **읽기 트래픽 분산** 및 **용도별(배치, 통계, 분석 등) 레플리카 분리**에 활용됩니다.
        - 하나의 레플리카는 항상 예비용으로 남겨두는 것이 좋습니다.
    - **16.6.3 체인 복제 구성 (Chain Replication Configuration)**
        - 레플리카 서버가 다시 다른 레플리카의 소스 서버 역할을 하는 계층 구조입니다.
        - **소스 서버의 바이너리 로그 배포 부하를 줄여주는 역할**을 합니다.
        - 하드웨어/버전 업그레이드 시 서비스 중단 없이 시스템을 전환하는 데 유용합니다.
    - **16.6.4 듀얼 소스 복제 구성 (Dual Source Replication Configuration)**
        - 두 MySQL 서버가 서로에게 소스이자 레플리카가 되어 양쪽에서 쓰기 작업이 가능합니다.
        - **Active-Passive** (장애 시 빠른 전환) 또는 **Active-Active** (지리적 분산 환경에서 쓰기 지연 감소) 형태로 사용됩니다.
        - Active-Active 모드에서는 데이터 충돌(Conflict) 관리에 주의해야 하며, 쓰기 확장성(write scalability)을 위해서는 샤딩(Sharding)이 권장됩니다.
    - **16.6.5 멀티 소스 복제 구성 (Multi Source Replication Configuration)**
        - 하나의 레플리카 서버가 둘 이상의 소스 서버를 갖는 형태입니다.
        - **여러 MySQL 서버에 존재하는 데이터를 하나의 서버로 통합**하거나, 샤딩된 테이블 데이터를 통합, 또는 여러 서버의 데이터를 한 곳에서 백업하는 데 사용됩니다.
        - 소스 서버 간 변경 이벤트 충돌 여부를 사전에 검토해야 합니다.
- **16.7 복제 고급 설정 (Advanced Replication Settings)**
    
    - **16.7.1 지연된 복제 (Delayed Replication)**
        - 의도적으로 소스-레플리카 간 복제를 지연시키는 기능입니다.
        - 개발자/DBA 실수로 인한 데이터 삭제 등 **예기치 못한 문제 발생 시 복구 시점 제공**에 유용합니다.
        - MySQL 8.0부터는 `original_commit_timestamp`(OCT) 값을 활용하여 지연 시간을 정확하게 계산합니다.
    - **16.7.2 멀티 스레드 복제 (Multithreaded Replication)**
        - 레플리카 서버가 여러 SQL 워커 스레드를 사용하여 트랜잭션을 병렬로 적용할 수 있게 합니다.
        - **코디네이터 스레드(Coordinator Thread)**가 릴레이 로그에서 이벤트를 읽어 **워커 스레드(Worker Thread)**에 할당합니다.
        - **데이터베이스 기반 멀티 스레드 복제**: 데이터베이스 단위로 병렬 처리를 수행하며, 데이터베이스가 하나뿐인 경우 장점이 없습니다.
        - **논리적 클럭(LOGICAL CLOCK) 기반 멀티 스레드 복제**: `commit_seq_no`, `last_committed`, `sequence_number`와 같은 논리적 순번 값을 이용하여 트랜잭션의 병렬 처리 가능 여부를 판단합니다.
            - **Commit-parent 기반**: 소스에서 그룹으로 커밋된 트랜잭션 수에 따라 레플리카의 병렬 처리율이 향상됩니다.
            - **잠금(Lock) 기반**: 선행 트랜잭션의 상태를 고려하여 병렬 처리 가능 여부를 판단합니다.
            - **WriteSet 기반**: 각 트랜잭션이 변경한 데이터(WriteSet)를 기반으로 병렬 처리 종속 관계를 정의하여, 서로 다른 데이터를 변경한 트랜잭션은 병렬로 처리될 수 있도록 합니다. 이는 복제 구조 내 병렬 처리량을 크게 향상시킬 수 있습니다.
        - `slave_preserve_commit_order` 변수는 소스에서 커밋된 순서와 동일하게 레플리카에 적용되도록 보장합니다.

### 16.7.1 지연된 복제 (Delayed Replication)
복제 목적 : 최대한 빨리 동일한 상태로
- 레플리카를 이용한 장애 복구가 수월

복제 지연?
- 큰 일 났을 때, 레플리카의 지연된 데이터를 사용해서 장애복구 수행
- 데이터베이스 과부하 상황에서의 지연 테스트

CHANGE_REPLICATION SOURCE TO 구문에 SOURCE_DELAY를 사용
```mysql
-- // MySQL 8.0.23 미만 버전
mysql> CHANGE MASTER TO MASTER_DELAY=86400;

-- // MySQL 8.0.23 이상 버전
mysql> CHANGE REPLICATION SOURCE TO SOURCE_DELAY=86400;
```

MySQL 8.0 버전부터는 바이너리 로그에 타임스탬프가 추가
- original_commit_timestamp(OCT)  
	- 트랜잭션이 원본 소스 서버(Original Source)에서 커밋된 시각
	- 밀리초 단위의 유닉스 타임스탬프
- immediate_commit_timestamp(ICT)  
	- 트랜잭션이 직계 소스 서버(Immediate Source)에서 커밋된 시각
	- 밀리초 단위의 유닉스 타임스탬프 값으로 저장된다.


>[!info] 원본 소스 서버? 직계 소스 서버?
> 3대가 체인 복제 구성으로 있을 때,
> 바로 위의 소스 서버가 직계 소스 서버,
> 가장 위에 존재하는 서버 (트랜잭션이 제일 먼저 실행) = 원본 서버


SHOW REPLICA STATUS 로 확인 가능

지연된 복제를 사용하더라도,
- 소스 서버의 바이너리 로그가 레플리카의 릴레이 로그 파일로 바로 복사된다.
- 레플리케이션 SQL 스레드가 복제된 이벤트들에 대한 실행을 지연할 뿐.
- 그래서 복제 지연이 되어 있더라도, 소스 서버 장애시에 레플리카를 이용해서 복구할 수 있다!

### 16.2.7.2 LOGICAL CLOCK 기반 멀티 스레드 복제
(*책에 16.2.7.2.2 라고 오타있으니 수정하세요~*)
데이터베이스 기반 처리 방식의 문제
- 단일 데이터베이스인 경우 의미없음.
- 여러 개 의 데이터베이스를 아우르는 DML일 경우 대기 발생
- 특정 데이터베이스 쿼리가 집중되면, 지연이 발생함.

> [!info] LOGICAL CLOCK?? 
> 시간이 t1, t2, t3 처럼 주어지면, 우리는 선후 관계만 판단할 수 있다.
> t1과 t2 사이에 진짜 시간이 얼마나 흘렀는지,
> t2 - t1 이 큰지? t2 - t3 이 큰 지 모른다.
> **즉, 시간의 선후 관계만 판단 할 수 있는 것이 LOGICAL CLOCK**
> *반대 되는 개념으로는 Wall Clock*

트랜잭션이 BINLOG로 기록된 때, 논리적인 순번 값을 부여해,
병렬로 실행할 수 있게 하는 방식

#### 16.2.7.2.1 바이너리 로그 그룹 커밋

![[Pasted image 20250713203716.png]]

클라이언트로부터 커밋 요청이 들어오면 
Prepare 와 Commit 두 단계로 커밋을 처리합니다.
**이를 분산 트랜잭션(XA, Two-Phase Commit) 이라 한다.**

![[Pasted image 20250713203915.png]]

큐의 첫번 째 트랜잭션을 Leader 라고 한다.
그 이후 등록된 트랜잭션은 Follower 라고 한다.
팔로워는 리더에게 자신의 트랜잭션 처리에 대한 모든 것을 일임한다.
리더는 모든 팔로워를 가져와 처리하고 다음 큐로 이동한다.
다음 큐에 이동하였을 때, 큐가 비어있지 않으면, 리더는 팔로워가 된다.

Flush 단계
- 대기 큐에 등록된 각 트랜잭션들을 순서대로 binlog에 기록한다.

Sync 단계
- 앞서 기록된 바이너리 로그 내용들을 디스크와 동기화하는 fsync() 시스템 콜을 수행한다.

Commit
- 대기 큐에 등록된 트랜잭션에 대해 스토리지 엔진 커밋을 진행한다.

#### 16.7.2.2.4 WriteSet 기반 Logical clock
트랜잭션이 변경한 데이터를 기준으로 병렬 처리 가능 여부를 결정

기존 방식에서는 커밋 처리 시점이 다르면 다른 데이터를 변경해도 병렬로
수행할 수 없었음.

`binlog_transaction_dependency_tracking`

COMMIT_ORDER
- 기존 방식
WRITESET
- 서로 다른 데이터 변경한 트랜잭션들은 모두 병렬로 처리 가능
WRITESET_SESSION
- 동일한 세션에서 실행된 트랜잭션들은 병렬로 처리될 수 없다.
- 그 외에는 WRITESET이랑 같음

트랜잭션 간의 종속 관계를 정의하는데, 이를 WriteSet이라고 한다.
![[Pasted image 20250713214412.png]]

WriteSet은 테이블에 존재하는 유니크한 키의 개수만큼 만들어진다.

HashMap 형태로, WriteSet-sequence_number 형식으로 저장함.
![[Pasted image 20250713214555.png]]

1. 히스토리 테이터를 찾는다.
2. 충돌하면, 
	1. table의 값을 자신의 sequence_number 로 변경하고,
	2. table에 있던 값이 자신의 last_commited 값 비교
		1. 크면 last_commited를 table의 값으로 바꾼다.
		2. 작으면, last_commited를 바꾸지 않는다.

결국, 트랜잭션의 last_commited에는 제일 큰 seq_number가 쓰인다.

> WRITESET_SESSION 의 다른 점

last_commited 값을 같은 세션에서 커밋된 마지막 트랜잭션의 **sequence_number 값과 한번 더 비교해서 둘 중 큰 값을 선택**해, 
최종적으로 last_commited에 저장한다.

    - **16.7.3 크래시 세이프 복제 (Crash-safe Replication)**
        - MySQL 서버가 비정상 종료된 후에도 복제가 원활하게 진행될 수 있도록 하는 설정 조합을 의미합니다.
        - 주요 설정: `sync_binlog=1`, `innodb_flush_log_at_trx_commit=1`, `relay_log_info_repository = TABLE`, `master_info_repository = TABLE`, `relay_log_recovery = ON`, `sync_relay_log=1` 등입니다.
        - 특히 `sync_relay_log=1`은 멀티 스레드 복제에서 트랜잭션 갭(Gap) 발생을 방지하는 데 중요합니다.
    - **16.7.4 필터링 된 복제 (Filtered Replication)**
        - 특정 데이터베이스나 테이블을 복제 대상에 포함하거나 제외할 수 있는 기능입니다.
        - `binlog-do-db`, `binlog-ignore-db`, `replicate-do-db`, `replicate-ignore-db` 등의 옵션을 사용합니다.
        - Statement 또는 Mixed 바이너리 로그 포맷 사용 시 필터링 처리 결과가 쿼리의 컨텍스트에 따라 달라질 수 있으므로 주의가 필요합니다.
