# 2.1 네트워크 애플리케이션의 원리
- 다른 위치의 종단 시스템에서 동작
- 네트워크를 통해 서로 통신
- 서버 - 클라이언트 구조
- 
## 2.1.1 네트워크 애플리케이션 구조
- 애플리케이션 구조와 네트워크 구조는 다르다.
### 클라이언트-서버 구조
- 서버
	- 항상 동작하는 호스트
	- (고전적 구조) 클라이언트로부터 서비스 요청을 받는다.
	- 고정된 IP 주소를 갖는다.
- 클라이언트
	- 항상 또는 가끔 켜져 있는 호스트
	- (고전적 구조) 서비스를 요청하는 주체
### P2P 구조
- peer 끼리 통신
- 자가 확장성 (self-scalability)
## 2.1.2 프로세스 간 통신
- 운영체제에서 실제 통신하는건 프로세스
- 메시지 교환으로 서로 통신한다.
### 클라이언트와 서버 프로세스
- 클라이언트 - 서버 구조로 표현한다.
- 클라이언트
	- 통신을 초기화 하는 프로세스
- 서버
	- 세션을 시작하기 위해 접속을 기다리는 프로세스
### 프로세스와 컴퓨터 네트워크 사이의 인터페이스![[Pasted image 20250125182339.png]]
- 소켓
	- 프로세스는 집, 소켓은 출입구
	- 애플리케이션 계층과 트랜스포트 계층 간의 인터페이스
- 트랜스포트 계층에 대한 통제
	1. 트랜스포트 프로토콜 선택
	2. 매개변수 설정 (최대 버퍼와 최대 세그먼ㄴ트 크기 등)
### 프로세스 주소 배정
- 수신 프로세스 식별 위한 정보
	1. 호스트의 주소 **(= IP주소)**
	2. 목적지 호스트 내 수신 프로세스의 식별자 **(= 포트)**
		- 웹 80, SMTP 25

## 2.1.3 애플리케이션이 이용 가능한 트랜스포트 서비스
- 4가지 차원으로 분리할 수 있다.
	- 신뢰적 데이터 전송, 처리율, 시간, 보안
### 신뢰적 데이터 전송
- 네트워크에서 손실될 수 있다.
	- 라우터 버퍼 오버플로, 비트 이상으로 버려짐 등
- **신뢰적 데이터 전송 : 보장된 데이터 전송 서비스를 제공한다**
	- Reliable data transfer
- 손실 허용 애플리케이션도 있다.
### 처리율
- 가용 처리율은 시간에 따라 변동한다.
- 어느 정도 명시된 속도에서 가용 처리율을 제공한다.
	- 보장된 처리율을 제공한다. (최소 X bps 이상)
- 대역폭 민감 애플리케이션
	- bandwidth-sensitive application
	- 많은 멀티미디어 애플리케이션들
- <> 탄력적 애플리케이션
	- elastic application
	- 대역폭에 민감하지 않은 애플리케이션 (그럼에도 대역폭이 넓을수록 좋다)
	- 전자메일, 파일 전송, 웹 전송 등
### 시간
- 수신자의 소켓에 100ms내로 도착하는 것을 보장
	- 실시간 상호작용 애플리케이션
### 보안
- 하나 이상의 보안 프로세스 제공할 수 있다.
	- 송신 프로세스가 전송하는 모든 데이터 암호화
	- 수신 트랜스포트 계층에서 해독
- 기밀성 (confidentially), 데이터 무결성 (integrity), 종단 인증 (authentication)
## 2.1.4 인터넷 전송 프로토콜이 제공하는 서비스
- UDP, TCP
### TCP 서비스
- **연결지향형** 서비스
	- 핸드셰이킹 : 클라이언트와 서버가 서로 전송 제어 정보를 교환
	- 교환 정보로 TCP 연결 생성
	- 서로 메시지를 보낼 수 있음 (**전이중 (full-duplex) 연결**)
- **신뢰적인 데이터 전송** 서비스
	- 올바른 순서로 전달
	- 중복이나 손실을 막는다.
- 혼잡 제어 서비스
	- 네트워크가 혼잡하면 프로세스(클라이언트 또는 서버) 속도를 낮춘다.
	- 각 연결이 네트워크를 공평히 사용할 수 있도록 한다.
### UDP 서비스
- 비연결형 서비스
	- 핸드셰이킹 안함
- 비신뢰적 데이터 전송 서비스
	- 송신하면, 수신되는걸 보장하지 않는다.
	- 순서가 뒤바뀔수도 있다.
- 혼잡 제어 비포함
	- 원하는 속도로 네트워크 계층에 보낼 수 있다.
	- 그러나, 종단 간 처리율은 이 속도보다 작아질 수 있다.
### 인터넷 트랜스포트 프로토콜이 제공하지 않는 서비스
- 처리율, 시간 보장 서비스가 빠져있다.
	- 하지만 애플리케이션들이 대역폭 민감, 시간 민감 하더라도, 잘 대처
## 2.1.5 애플리케이션 계층 프로토콜
- 애플리케이션 계층 프로토콜
	- 교환 메시지 타입
	- 여러 메시지 타입의 문법
	- 필드의 의미 (정보의 의미)
	- 언제, 어떻게 프로세스가 메시지를 전송하고, 메시지에 응답하는 지 결정
- HTTP : RFC 7230
	- HTTP를 제외한 많은 애플리케이션 프로토콜은 독점, 비개방적이다.
- 네트워크 계층 프로토콜과 애플리케이션 계층 프로토콜을 구별하는 것은 중요하다.
	- HTTP는 웹 애플리케이션의 한 요소이다.
	- 넷플릭스에서 DASH는 애플리케이션의 한 요소(하지만 중요한 요소)이다.

## 2.2.1 HTTP 개요
- RFC 1945, RFC 7230, RFC 7540에 정의
- 서버와 클라이언트로 구성
- 웹 페이지는 객체로 구성
	- 객체 : 단일 URL로 지정할 수 있는 파일 (HTML, JPEG, JS, CSS 등)
- HTTP는 TCP를 사용한다.
	- 클라이언트는 우선 서버에 TCP 연결 시작
	- 연결되면, 서로의 소켓 인터페이스를 통해 TCP로 접속
	- HTTP는 TCP가 어떻게 내부적으로 작동하는지 걱정할 필요 없다.
- HTTP는 상태 정보를 저장하지 않는다.
	- Stateless protocol
- HTTP/1.1 사용 중
	- HTTP/2 많이 사용한다.
## 2.2.2 비지속 연결과 지속 연결
- 계속 연결을 지속해야 하는가, 말아야 하는가?
### 비지속 연결 HTTP
- 비지속 연결 과정
	1. HTTP 클라이언트는 80을 통해 TCP 연결 시도
		1. 소켓 생성
	2. HTTP 클라이언트는 소켓으로 HTTP 요청 메시지 전송
	3. HTTP 서버는 연결 소켓으로 요청 메시지 수신
		1. 수신
		2. 객체 추출
		3. 캡슐화
		4. 소켓을 통해 클라이언트로 전송
	4. HTTP 서버는 TCP에게 TCP 연결 끊으라고 지시
		1. 그러나 실제로 TCP클라이언트가 응답 메시지를 올바로 받을 때까지 끊지 않음.
	5. HTTP 클라이언트가 응답 메시지를 받으면, TCP 연결이 중단
		1. 응답 메시지로부터 파일 추출, 파일 조사, 객체 참조 찾음
	6. 그 후 참조 객체에 대해서 반복 수행
- HTTP는 HTTP 클라이언트와 HTTP 서버 사이만 정의
- HTTP/1.0 은 비지속 연결을 지원
	- 앞선 예시에서 11개 생성 (1+10)
- 클라이언트는 동시에 10개를 TCP 연결을 생성할 수도, 순차적으로 생성할 수도 있다.
	- 브라우저 따라 다르다.
	- 응답시간을 줄일 수 있다.
- RTT![[Pasted image 20250125192510.png]]
	- Round-trip time
	- 클라이언트부터 서버까지 갔다가, 다시 되돌아오는데 걸리는 시간
	- 패킷 전파 지연, 패킷 큐잉 지연, 패킷 처리 지연 등을 포함
- TCP 연결
	- 3 way handshake
### 지속 연결 HTTP
- 비지속 연결의 단점
	- 각 요청 객체에 대한 새로운 연결이 결정, 유지되어야 한다.
	- 각 객체에 대해 2 RTT를 필요로 한다.
- HTTP/1.1 지속 연결
	- 응답 보낸 후에 연결 유지
	- 여러 웹페이지를 같은 연결상에서 받는다.
- 파이프라이닝
	- 객체에 대한 요구는 진행 중인 요구에 대한 응답을 기다리지 않고 계속해서 만들어질 수 있다.

## 2.2.6 HTTP/2
- RFC 7540
- 주요 목적
	- 하나의 TCP 연결상에서 멀티플렉싱 요청/응답 지연 시간 줄이기
	- 요청 우선순위화, 서버 푸시, 헤더 효율적 압축 등 제공
- HTML/1.1 에서 발생할 수 있는 HOL 블로킹 문제
	- Head Of Line 블로킹
	- TCP 연결이 하나일 때, 앞쪽에 큰 객체가 있다면, 다음 객체들을 블로킹한다.
	- HTML/1.1 여러 TCP연결을 이용하여 해결
- TCP 혼잡 제어도 브라우저에게 예상치 못한 혜택
### HTTP/2 프레이밍
- HOL 블로킹 문제를 해결하기 위해 등장한 HTTP/2 
- 각 메시지를 작은 프레임으로 나누고, 같은 TCP 연결에서의 요청과 응답 메시지를 인터리빙한다.
- 프레이밍은 HTTP/2 프로토콜의 프레임으로 구현된 다른 프레이밍 서브 계층에 의해 이루어짐
	- 헤더 필드, 메시지 본문을 각각 프레임으로 쪼갬
	- 응답 프레임들은 서버 프레이밍 서브 계층에 의해 인터리빙됨
	- 응답은 클라이언트 프레이밍 서브 계층에서 재조립, 브라우저에 의해 처리
	- 프레임을 바이너리 인코딩
		- 파싱 효율
		- 에러 강건
### 메시지 우선순위화 및 서버 푸싱
- Message prioritization
- 클라이언트가 1에서 256 사이의 가중치를 부여함으로써 요청에 우선순위 부여
	- 서버는 가중치 높은 프레임을 제일 먼저 보낼 수 있다.
- 서버는 클라이언트의 요청 없이도 추가적인 객체를 클라이언트에게 보낼 수 있다.

## 2.4.1 DNS가 제공하는 서비스
- 호스트 이름을 IP주소로 변환해주는 인터넷 DNS
- DNS
	1. DNS 서버들의 계층구조로 구현된 분산 데이터베이스
	2. 호스트가 분산 데이터베이스로 질의하도록 허락하는 애플리케이션 계층 프로토콜
- DNS 서버는 주로 BIND 소프트웨어를 수행하는 UNIX 컴퓨터
	- Berkeley Internet Name Domain
	- UDP, Port 53
- URL을 IP로 변환하기 위해 이용
	1. 브라우저는 호스트 이름을 DNS 애플리케이션 클라이언트(호스트 PC)측에 넘긴다.
	2. DNS 클라이언트는 호스트 이름을 DNS 서버로 질의
	3. DNS 클라이언트는 IP주소로 응답받음
	4. DNS로부터 주소 받으면 브라우저는 TCP 연결 초기화
- 가까운 DNS서버에 캐싱되어있다.
- 다른 기능들
	- 호스트 에일리어싱 (host aliasing)
		- 별칭 허용
	- 메일 서버 aliasing
		- 별칭 허용
	- 부하 분산
		- 여러 서버 IP중 하나 응답
- RFC 1034 및 다른 RFC 에서 갱신
